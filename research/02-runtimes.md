# Isolation runtimes other than Firecracker — state as of 2026-08-13

*Research report 2 of 6 for the Substrate architecture plan. Produced 2026-08-13. Primary sources preferred; [UNVERIFIED] marks what could not be traced; "possibly stale" flags sources older than 18 months.*

## 1. Cloud Hypervisor (CH)
- **Version/cadence:** v53.0 released **2026-07-12**; v52.0 2026-05-14, v51.0 2026-02-20, v50.0 2025-12-19, v49.0 2025-11-09 → roughly 6–10 week major cadence plus point releases. ([blog index](https://www.cloudhypervisor.org/blog/), [v53.0](https://www.cloudhypervisor.org/blog/cloud-hypervisor-v53.0-released/))
- **Boundary:** hardware virt. Runs on **KVM or MSHV (Microsoft Hypervisor)**; x86-64 + AArch64, RISC-V experimental; needs `/dev/kvm` (or MSHV) — no pure-userspace mode. Guest kernel must be PVH or bzImage. ([README](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/README.md))
- **Snapshot/restore:** mature and actively invested in. v53.0 adds an **offloaded snapshot/restore daemon** (external process), **background prefault** after userfaultfd restore, and **VFIO migration v2** for migratable devices. v52.0 keeps untouched guest pages as file holes (smaller snapshots, faster restore) and adds auto-`resume=true`. Two restore modes: eager-copy (default) and `memory_restore_mode=ondemand` via userfaultfd. Limits: orchestrator-supplied network FDs are not plumbed through `vm.receive-migration` (offload path unusable); **confidential VMs cannot use offload snapshot/restore**. ([docs/snapshot_restore.md](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/main/docs/snapshot_restore.md))
- **Live migration:** separate, first-class — v53.0 adds **postcopy** remote migration, **mTLS-encrypted** migration, post-migration network announcements, non-blocking migration API.
- **Device breadth vs Firecracker:** materially wider — virtio net/block/pmem/fs/vsock/**rtc**, **VFIO passthrough**, **PCI hotplug**, Windows guests (Win10/WS2019). README explicitly positions CH at general cloud workloads vs Firecracker at container/serverless.
- **Production users:** **Azure Confidential Containers on AKS** stack is "Microsoft hypervisor + nested VMs + Cloud-Hypervisor as VMM + Kata/Kata CoCo" ([MS Learn](https://learn.microsoft.com/en-us/azure/aks/confidential-containers-overview)); CH is a supported Kata VMM.
- **Per-VM memory overhead: [not found]** in primary sources — do not borrow Firecracker's <5 MiB figure.

## 2. libkrun
- **Version:** stable line **v1.19.4**, built **2026-07-03** (Arch pkg `libkrun 1.19.4-1`, 2026-07-03; recent tags v1.19.0 → v1.19.4 over Jun–Jul 2026). `main` is **2.0**, API/ABI-incompatible with 1.x and still unstable; README says use the newest `stable-*` branch in production. ([releases](https://github.com/containers/libkrun/releases), [Arch](https://archlinux.org/packages/extra/x86_64/libkrun/), [README](https://github.com/containers/libkrun))
- **Boundary:** hardware virt, embedded as a **library in your process** — KVM on Linux, **HVF on macOS/ARM64**. Security model explicitly treats **guest + VMM as one security context**; host isolation still requires namespaces/seccomp around the VMM process. Windows/WHP support is claimed by third parties — **[UNVERIFIED]** against the README.
- **Users (per README):** `crun` (krun handler), **krunkit** (GPU-enabled macOS VMs, the podman-machine GPU provider), **muvm**. RamaLama/podman are not named in the README itself.
- **Snapshot:** **no snapshot/restore in stable 1.x** — absent from README and from all v1.18–v1.19.4 release notes. A `feat(snapshot): finalize descriptor and api contract` commit lands on the 2.0 branch in **July 2026**, i.e. in-development. Third-party "sub-ms restore" claims are **[UNVERIFIED]**/contradicted.
- **Arbitrary Linux binaries:** partial by design — README states compatibility with "a reasonable amount of workloads" and lists "compatible with all kinds of workloads" as an explicit **non-goal**. TEE variants: libkrun-sev (SEV), libkrun-tdx (TDX). Needs `/dev/kvm` on Linux, HVF entitlement on macOS.

## 3. Kata Containers
- **Version:** **4.0.0 released 2026-07-22** — Go runtime → **Rust `runtime-rs`** is now the default runtime; Go runtime deprecated, removal no earlier than 5.0.0 (~Q1 2028). Preceding 3.2x/3.3x line shipped roughly every 3–5 weeks. ([4.0.0 blog](https://katacontainers.io/blog/kata-containers-4-0-0-release-overview/))
- **Default VMM — flagged discrepancy:** 3.30.0 release notes say "**runtime-rs: set QEMU as the default hypervisor**"; the 4.0 blog describes **Dragonball** as the "default built-in VMM" (built-in = in-process VMM library, its long-standing tagline). Treat QEMU as the shipped default for runtime-rs and Dragonball as the in-process option. Supported VMMs: **QEMU, Cloud Hypervisor, Dragonball, Firecracker, StratoVirt** ([docs/hypervisors.md](https://github.com/kata-containers/kata-containers/blob/main/docs/hypervisors.md)); that doc states QEMU is "the best supported hypervisor for NVIDIA GPUs and confidential computing."
- **Memory overhead:** best primary-ish numbers from the AWS multi-tenancy sample: RuntimeClass `overhead.podFixed` = **160 MiB + 250m CPU**; measured **~334 MiB physical RAM for an idle pod** (QEMU ~282 MiB, virtiofsd ~8 MiB, containerd-shim-kata ~44 MiB). ([aws-samples doc](https://github.com/aws-samples/sample-multi-tenancy-openclaw-on-eks/blob/main/docs/kata-containers.md)) Kata publishes no official per-sandbox memory/boot table.
- **Boot time:** no primary Kata figure found. Commonly cited 150–500 ms (QEMU) figures live only in the SEO/blog tier → **[UNVERIFIED]**. (The "8–12 minutes" in the AWS doc is EC2 **bare-metal instance** provisioning, not pod boot — do not use it.)
- **Confidential containers:** AMD SEV/SEV-ES/**SEV-SNP** and Intel **TDX** in production-grade runtime classes (`kata-qemu-snp`, `kata-qemu-tdx`, `kata-clh-tdx`, `kata-qemu-nvidia-gpu-snp`, `kata-qemu-coco-dev`); **Arm CCA** still pending hardware availability. Note: the hypervisors.md TEE matrix extraction showed CH as TDX-unsupported while a `kata-clh-tdx` class exists — treat the per-VMM matrix as unresolved; resolve against `configuration-*.toml` defaults in the 4.0 tree before designing around it.
- Needs `/dev/kvm` (all VMM options). Runs arbitrary Linux binaries — real guest kernel.

## 4. gVisor (runsc)
- **Platforms:** **systrap is default since mid-2023** (seccomp `SECCOMP_RET_TRAP` + trampoline patching of `syscall` instructions). **ptrace is no longer supported and slated for removal.** KVM platform is optional, best on bare metal, poor under nested virt — so **gVisor generally does NOT need `/dev/kvm`**, which is its key portability edge. ([platforms guide](https://gvisor.dev/docs/architecture_guide/platforms/), [systrap blog, 2023-04-28 — possibly stale](https://gvisor.dev/blog/2023/04/28/systrap-release/))
- **directfs** (2023-06-27, possibly stale) removes gofer RPC round-trips by donating FDs to the Sentry; now the default. ([blog](https://gvisor.dev/blog/2023/06/27/directfs/))
- **Syscall numbers:** the official [performance guide](https://gvisor.dev/docs/architecture_guide/performance/) still benchmarks on **GCE n1-standard-4 / Debian 9 / kernel 4.19 and largely on ptrace** — methodologically stale; it gives graphs, not extractable per-syscall figures. The systrap post likewise publishes graphs (getpid, ABSL build, FFmpeg, TensorFlow, Redis) without numeric deltas in text. Per-sandbox memory is described only as "a small, mostly fixed amount"; the widely repeated **50–100 MiB/sandbox** figure appears only in the SEO tier → **[UNVERIFIED]**.
- **Checkpoint/restore:** supported and improving — background restore (run as soon as kernel state loads, memory async), compression (`none` default, `flate-best-speed`), O_DIRECT, zero-page skipping, **cross-CPU-feature restore** via `dev.gvisor.internal.cpufeatures`, GPU checkpoint via NVIDIA `cuda-checkpoint` (not arm64). Gap: **containerd CRI + containerd-runsc-shim `CheckpointContainer` not implemented** (open as of mid-2025). ([docs](https://gvisor.dev/docs/user_guide/checkpoint_restore/))
- **Arbitrary binaries:** subset of the Linux ABI. Known gaps: cgroup *enforcement*, mounting ext4/fat32 block devices, partial iptables, io_uring off by default, no KVM-in-sandbox, no arbitrary passthrough hardware (NVIDIA GPU + TPU excepted). Passes regression suites for Python/Java/Node/PHP/Go. ([compatibility](https://gvisor.dev/docs/user_guide/compatibility/))
- **Scale users:** Google (GKE Sandbox, Cloud Run, App Engine), **Anthropic (claude.ai code execution)**, **OpenAI**, **Cloudflare (Pages builds)**, DigitalOcean App Platform, Modal, Ant Group, Northflank, Tines, Beam. ([gvisor.dev/users](https://gvisor.dev/users/)) **GKE Agent Sandbox** (2026-05-21) is gVisor-native: **300 sandboxes/sec/cluster**, **p90 allocation 200 ms** (with warm pool), Pod Snapshots for suspend/resume, **16× sandbox growth in <5 months**. ([Google Cloud blog](https://cloud.google.com/blog/products/containers-kubernetes/bringing-you-agent-sandbox-on-gke-and-agent-substrate)) Modal: gVisor checkpoint/restore cut torch-import cold start ~5 s → **1.05 s p50**, SD inference 13 s → 3.5 s; snapshot "pages" files 100 MiB–10 GiB; **no live sockets, no GPU state**, CPU-feature sensitivity. (2025-01-28 — right at the staleness line)

## 5. QEMU `microvm` machine type
- Minimalist machine, **no PCI, no ACPI**, Firecracker-inspired, "designed for short-lived guests"; ISA bus + LAPIC/IOAPIC/kvmclock/fw_cfg + **up to 8 virtio-mmio devices**; **qboot** BIOS by default for boot time. Explicitly **no hotplug and no live migration across QEMU versions**; firmware can't boot from virtio-mmio block, so host-side kernel+initrd required. ([QEMU docs](https://www.qemu.org/docs/master/system/i386/microvm.html))
- **Boot time:** QEMU's own docs make no numeric claim ("a baseline for benchmarking"). Fastest published data point is a **~3 ms OSv ROFS boot on microvm** — a unikernel guest, not Linux. Needs `/dev/kvm` for kvmclock/perf. **Nobody appears to be building a multi-tenant sandbox platform on it in 2026** — the projects that want this reach for CH, Firecracker, Dragonball or libkrun instead; QEMU-with-full-machine remains Kata's default.

## 6. WASM runtimes
- **Wasmtime v47.0.3, 2026-07-31** (v47.0.0 2026-07-20; monthly major on the 20th + patch releases; 47.0 enables Wasm GC and exception-handling by default). ([releases](https://github.com/bytecodealliance/wasmtime/releases))
- **Instantiation:** primary numbers from the CoW/memfd pooling-allocator work: **SpiderMonkey.wasm instance creation ~1.69 µs → ~773 ns → ~680 ns**; a `call_empty_function` end-to-end path measured 24–27 µs vs 4–5 µs for native instance reuse. ([PR #3697, Jan–Feb 2022 — stale, but the only primary µs figures](https://github.com/bytecodealliance/wasmtime/pull/3697)) Practical posture today: AOT-precompiled module + `InstancePre` + pooling allocator + CoW memory init → sub-ms instantiation; memory per instance is bounded by the pooling config (e.g. N memories × ≤2 GiB reservation, virtual not resident).
- **Isolation boundary: not a kernel boundary** — software fault isolation inside a host process. No `/dev/kvm`, runs anywhere including nested/VM-less environments. That's the whole trade.
- **"Arbitrary code" coverage — the binding constraint.** **WASI 0.3.0 released 2026-06-11** (native async in the Component Model: `async func`, `stream<T>`, `future<T>`; `wasi:io` folded into the Canonical ABI; supported in **Wasmtime 43+** and jco). **Threads are still roadmap** — cooperative first, then preemptive. ([wasi.dev/roadmap](https://wasi.dev/roadmap), [WASI 0.3](https://wasi.dev/releases/wasi-p3))
  - **No `fork`, no preemptive threads, no `dlopen`** in standard WASI. CPython specifically is blocked by absent dlopen/dlsym, which is why Emscripten (not WASI) is the dynamic-linking path — see PEP 776. Python runs on WASI as a static build minus native extensions.
  - **Node.js on WASI does not exist** in the reverse direction — Node ships a WASI *host* API (`node:wasi`), not a Node runtime compiled to WASI. Do not plan on it.
  - **Wasmer** ships **WASIX**, a nonstandard Preview1 fork adding **fork(), threads, Berkeley sockets**, plus Wasmer 6.0 (~95% of native on Coremark, zero-cost exceptions) and beta Python-on-Edge (Django/FastAPI). **WasmEdge** similarly predates the standard with nonblocking sockets/HTTP extensions. Both buy compatibility by leaving the standard.
  - Net: WASM covers request/response and plugin workloads, **not** "run this arbitrary container image."

## 7. New / notable entrants 2025–2026
- **Unikraft Cloud** — publicly launched **Oct 2025** with a $6M seed; claims **10 ms cold start** to first byte, "any Dockerfile" as a Linux-based microVM, scale-to-zero via **pre-initialized snapshots**, 100k+ VMs/server; runs a **modified Firecracker** VMM (so still KVM). At **QCon London, Mar 2026** they demoed waking **VM #1,000,000** on a commodity server in ~10 ms. ([unikraft.com/how-it-works](https://unikraft.com/how-it-works/), [InfoQ, 2026-03](https://www.infoq.com/news/2026/03/qcon-million-sandboxes-server/)) **Arbitrary unmodified Linux binaries: not confirmed by their docs** — the site talks Dockerfile workflow, not full binary compatibility; the Unikraft binary-compat layer historically covers a syscall subset. Treat as **[UNVERIFIED]** for arbitrary ELF workloads.
- **Edera** — Rust-rewritten stripped-down **Xen** ("Krata") providing per-workload **zones** with their own kernel; **KVM backend arriving summer 2026** for teams already on KVM. Distinct boundary: type-1 hypervisor + paravirt rather than KVM microVM. Academic writeup: *Goldilocks Isolation* ([arXiv 2501.04580, Jan 2025](https://arxiv.org/html/2501.04580); [Edera KVM architecture](https://docs.edera.dev/technical-overview/architecture/kvm/)).
- **microsandbox** (Super Rad Co., ex-Zerocore) — libkrun-based, self-hosted microVM runtime for agent code. README: **"average boot times under 100 ms," measured as guest boot on an M1**; platforms macOS (Apple Silicon), Linux (KVM), Windows (WHP); explicitly **beta**, breaking changes expected; **no snapshot support documented**. Third-party numbers differ widely (320 ms bare-metal Linux, "sub-200 ms") → spread is real, condition-dependent. ([README](https://github.com/microsandbox/microsandbox))
- **StratoVirt** (openEuler/Huawei, Rust) — claims **<50 ms microVM start** and **<4 MB memory footprint**; a supported Kata VMM. Numbers are unchanged across openEuler 20.09→25.09 docs, so they are **repeated marketing constants rather than fresh measurements** — treat as vendor claims. ([openEuler 25.09 docs](https://docs.openeuler.org/en/docs/25.09/virtualization/virtulization_platform/stratovirt/stratovirt_introduction.html))
- **Dragonball** — exists only as an in-process Rust VMM library inside Kata's `runtime-rs`; no credible standalone-product story found.
